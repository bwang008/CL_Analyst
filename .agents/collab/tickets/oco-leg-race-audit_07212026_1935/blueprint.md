## 1. Bug Summary — the issue is REAL

### 1.1 Primary defect (D1): protective-leg OCO is software-only, post-hoc, fire-and-forget
Each position's TP (LMT) and SL (STP) are two fully independent broker orders — no `parentId`, no `ocaGroup` (`src/live_execution/ibkr_client.py:1572-1641`). One-cancels-other exists only in application code: `LiveTrader._on_standard_execution_event` reacts to a **full** `Filled` status (`src/live_execution/live_trader.py:6366`) by bulk fire-and-forget cancel (`:6448` -> `cancel_open_cl_orders`, `ibkr_client.py:687-706` — no cancel-ack wait) and immediately resets state (`:6472`). Nothing bounds the interval during which BOTH closing orders are simultaneously live against one position.

Reachable failure sequences (all verified in current `development` source):
- **R1 — fast whipsaw:** leg A fills at the venue; leg B stays live for the full fill-event -> handler -> cancel round-trip (tens–hundreds of ms; seconds when the event loop is busy with bar inference). Price traverses both levels -> both fill -> account net-REVERSED. The codebase itself documents the cancel-in-flight fill hazard (`live_trader.py:1857-1865`, citing `ibkr_client.py:1583-1588`) — but only defends the time-barrier *exit order*, not the protective pair.
- **R2 — disconnect (highest likelihood):** both legs are GTC at the broker; during a socket outage the app cannot cancel anything and fill events are not observed. Window = entire outage. Live ledger evidence this class is common here: 6 `SL_HIT_OOB` + 5 `CLOSED_OOB_UNRECOVERED` of ~60 closes (~18% of exits filled outside the handler's observation window; read-only query, 2026-07-21).
- **R3 — partial fill:** software OCA acts only on `Filled`; a partially filled TP leaves the SL resting at FULL quantity against a reduced position -> an SL trigger then over-closes -> reversal by the filled amount. No code path resizes the sibling.
- **R4 — exit-vs-legs ordering:** `_check_time_barrier` cancels the legs fire-and-forget and IMMEDIATELY submits the close order in the same callback (`live_trader.py:1717-1738`); a leg fill crossing in flight + the exit fill = double close. Same cancel-then-act shape in the kill switch (`:6298-6318`).
- **Aftermath amplifier:** the second fill lands in the UNRECOGNIZED-FILL ignore branch (`:6473-6490`) because `_reset_position_state` already cleared the tracked ids (`:1288-1289`). The reversed position is then untracked: kill switch blind (`:6248` early-return on `_active_trade_id is None`), housekeeping UNTRACKED branch is detect-only/human-only (`:3176-3190`), and `_check_time_barrier` silently ADOPTS it as a fresh position (`:1701-1705`, called unconditionally at `:5039`) and would hold it — unprotected — up to `max_hold_bars` (~24h). Exposure compounding is bounded only by the max-position gate (`:5083-5087`).

### 1.2 Secondary defect (D2): sign-blind re-arm after a retired exit
`_route_retired_time_barrier_exit` branches only on `settled == 0` vs non-zero (`live_trader.py:2043-2047`); `_rearm_time_barrier_protection` re-places legs using the OLD tracked side and a STALE pre-settled quantity (`:2100-2113`, `current_position` read at `:1819` before the settled read). If the book has meanwhile REVERSED (R4 aftermath), re-arm places same-direction orders against the reversed book — protection that INCREASES exposure if it fills. No sign check exists.

### 1.3 Secondary defect (D3): tiered-rung fill mis-booked as full close (LATENT, armed by sizing)
All 5 live configs run `exit_mode: "TIERED"` (`configs/strategies/*.json` via `configs/fleet/fleet_manifest.json`; builder `live_trader.py:3381-3402`). On a multi-lot position the FIRST rung's `Filled` event is treated as full position closure: bulk cancel kills the SL and remaining rungs, state resets (`:6439-6472`) — remaining lots left naked and untracked. **Empirical mitigation today:** every live trade ever booked is 1-lot (ledger read-only query: all 66 rows `quantity=1`), and the rung allocator collapses 1 lot to a single rung (`:3384-3389`), so this has never fired. It arms itself the first time any model sizes >=2 lots, with no code change.

### 1.4 The prior-incident citation — CORRECTED
The $296k naked SI short (reconnect-false-flat-oob_07082026_0731, fixed `246c598`) was NOT this fill race: its mechanism was a stale-empty position cache read as flat -> the app cancelled BOTH live protective legs -> naked (not reversed) position. Same *family* — app-owned protection lifecycle acting on unconfirmed state — but a different mechanism, already fixed by settled-confirm gates. Broker-side OCA would NOT have prevented that incident and that fix does not close this race. Internal comments citing "the reconnect-false-flat-oob $296k class" for reversal risk (`live_trader.py:6263-6264`) conflate the two; this blueprint treats them as distinct.

### 1.5 Historical constraint reconstructed (REQUIRED context for any fix)
Commit `4a50a4f` (2026-03-25) deliberately REMOVED `parentId` + transmit-chaining from the children: children placed milliseconds after a fast entry fill referenced a parent already purged from IBKR's working-order table -> **Error 201 "Parent order is being cancelled"** -> rejected children -> naked position; reliably triggered by multi-partial fast fills. The replacement (standalone children + software OCA, `ibkr_client.py:1587-1596`) traded that failure for this race window. Two-phase placement (children priced from the ACTUAL fill, `place_entry_order` docstring `:1508-1512`) was and remains load-bearing. Also load-bearing: `triggerMethod=1` on the SL because IB-simulated stops mis-fired in low-liquidity overnight sessions (`:1484-1489`). A fix must preserve BOTH.

## 2. Recommended Fix — STAGED (per Impact-Reviewer; each stage its own ticket + authorization)

### Stage 1 (the load-bearing change): broker-native OCA group on the children
**Target:** `src/live_execution/ibkr_client.py::place_child_orders` (`:1572-1641`) only, plus tests and sim parity.
1. Generate an INDEPENDENTLY-UNIQUE OCA tag per bracket and set it on the SL and every TP order before `placeOrder` — e.g. `ocaGroup = f"OCA-{contract.localSymbol}-{client_id}-{uuid4().hex[:12]}"` (or epoch_ns in place of the uuid; the prefix is for log readability only, the uuid/ns component carries the uniqueness). **The group id MUST NOT be derived from `parent_order_id` (OPERATOR-CONFIRMED, cross-validated by the parallel proposal):** `_verify_and_heal_protective_legs` calls `place_child_orders(..., parent_order_id=0, ...)` with a literal hardcoded 0 on EVERY heal re-placement (`live_trader.py:2590`) — an id-derived tag would give every healed bracket across every symbol/process the identical group string, so a fill on one instrument's healed TP could cancel an UNRELATED instrument's SL (the 5 children share one account, and IBKR order ids are per-clientId sequences that collide across children anyway). `parent_order_id` may be LOGGED alongside the tag for audit joinability but never participates in its derivation.
2. `ocaType = 2` — **OPERATOR-CONFIRMED default** (remaining orders proportionately reduced in size WITH block — IBKR-held, one order routed at a time, overfill-protected). For the deployed 2-order group {1 TP, 1 SL} this is exact: full TP fill reduces SL to 0 (= cancel); partial TP fill reduces SL by the filled quantity (closes R3); enforcement is server-side, so it holds during disconnects (closes R2) and inside the app's reaction latency (closes R1). NO `parentId` — an `ocaGroup` is a free-standing sibling tag that never references the terminal parent order, so Error 201 is structurally impossible (see 3.1).
3. Keep the software OCA in `_on_standard_execution_event` unchanged as belt-and-braces (cancelling an already-dead order is benign/idempotent).
4. Keep `triggerMethod=1`, `tif=GTC`, `outsideRth=True` byte-identical.
5. **Startup config gate (no-silent-defaults rule):** if `exit_mode == "TIERED"` AND the instance can size >1 lot (`max_position_size > 1` or per-trade lots > 1), REFUSE to start with a config error naming this ticket. Rationale: multi-rung + single shared OCA group has ill-defined "proportionate" reduce semantics across mixed-size rungs, and multi-rung booking is separately broken (D3). Today every instance sizes 1 lot, so this gate blocks nothing live; it converts a silent future arming of D3 into a loud refusal until Stage 3 lands.
6. Sim parity: `simulated_execution.place_child_orders` (`:242+`) stamps the same group tag on its resting-order records; the sim's matching engine is already atomic-OCA (`:635-650`), i.e. it already models the POST-fix world — document that in the module docstring. Race-injection seams (a mode suppressing atomic OCA + partial fills) belong to Stage 2 tests, not the shipped sim default.
7. **OPERATOR-CONFIRMED (decision closed):** ocaType=2 "with block" is the default, under which IB may hold group members server-side rather than resting both natively at the exchange. This interacts with the `triggerMethod=1` overnight-stop rationale (`:1484-1489`). The paper canary is the GATE: it MUST verify overnight/off-hours stop states (no stuck `PreSubmitted`/`whyHeld='trigger'` pathology). Documented fallback if — and only if — the canary shows that pathology: `ocaType=3` (no block — both legs rest natively; IB still server-side-cancels the sibling on fill; residual overfill window shrinks from app-latency/outage-length to IB reaction time — still a strict improvement).
8. **Post-deploy verification hook (read-only):** extend `broker_audit.py` (clientId 626) to report `ocaGroup`/`ocaType` on resting protective legs, so broker-truth confirms group membership fleet-wide. (Presence-only today; it is quantity- and group-blind.)

### Stage 2 — REQUIRED companion (separate ticket; the COMMITTED IMMEDIATE follow-up, not indefinitely deferred)
**Operator-confirmed rationale:** a broker-side OCA guarantee with zero independent verification is itself a gap on a real-money system; the current silent UNRECOGNIZED-FILL drop is a defect regardless of Stage 1's effectiveness. Stage 2 ships as the next ticket after Stage 1's canary, not "eventually".
1. **Sibling-fill reversal branch instead of UNRECOGNIZED-ignore:** keep a bounded registry of recently-closed brackets (trade_id, sibling order ids, close reason, closed_at; snapshot the ids at the top of `_reset_position_state` BEFORE they are cleared; bounded lifetime — pruned on next entry / after N hours). A `Filled` event matching a registered sibling = confirmed double-fill: log CRITICAL + Telegram + health event, flatten the residual, book a truthful ledger row (reason e.g. `OCA_RACE_REVERSAL`, proven price via `get_executions`). Two MANDATORY conditions on this branch (operator-confirmed, from the parallel proposal's Impact-Reviewer; both re-verified against source):
   - **(2.1a) Un-gated shared flatten helper.** The flatten MUST be a NEW helper containing the actual flatten steps (cancel remaining orders, market-close, ledger close, CRITICAL Telegram, state reset) EXTRACTED from `_check_naked_position`'s body and called by BOTH `_check_naked_position` and this branch. Calling `_check_naked_position()` itself is a silent no-op here: by the time the stale second fill arrives, `_active_trade_id` is already `None` and its guard clause early-returns (`live_trader.py:6248`).
   - **(2.1b) Cached position read only.** This branch runs inside the ib_insync callback chain and MUST read position via `get_cached_position` (local cache), NEVER `get_position` — `get_position` routes through `ensure_connected` and can trigger a blocking reconnect, the "event loop is already running" failure class the settle-confirm work exists to avoid (the A-2 constraint documented at `live_trader.py:2990-2996`). No settled read from this context either — settled confirmation, if needed, belongs to the idle reconciler tick.
   DIVERGENCE from the Auditor's 2(ii) (upheld): `_reset_position_state` stays IMMEDIATE (no deferred-reset state machine) — deferring reset would entangle cooldown seeding (D2.4), re-entry gating, and the freshly-shipped kill-switch deferral keying (291a9fd), for no additional protection once Stage 1 exists.
2. **D2 sign check:** `_route_retired_time_barrier_exit` receives `settled` and refuses to re-arm when `sign(settled) != self._position_side` (or quantity mismatch): CRITICAL + health event + kill-switch-style flatten path instead of re-arm. `_rearm_time_barrier_protection` sizes from the SETTLED value, not the stale pre-settled read.
3. **Partial-fill observability:** non-`Filled` fill events (`filled_qty > 0`) on tracked legs log + emit a health event (booking stays unchanged; with ocaType=2 the sibling resize is broker-side).
4. DIVERGENCE from the Auditor's 2(i): KEEP the bulk symbol-scoped `cancel_open_orders` in the fill handler. Targeted-by-id is not load-bearing once broker OCA exists, and bulk-cancel call sites are pinned by a prior adjudication (`tests/test_oob_entry_state_recovery.py:108,1031,1288-1392`); reversing a pinned decision needs its own justification and buys nothing here.

### Stage 3 (tiered/multi-lot redesign; only if multi-lot sizing is ever wanted)
Per-tranche OCA PAIRS: split the SL into qty-matched rungs, one group per tranche ({TPi, SLi} with qi lots). Exact semantics by construction (rung i's TP kills rung i's SL only; net protection always equals net position) — also fixes D3's booking (rung fill = partial close, reduce tracked quantity; full reset only at zero). Requires: trailing-modify loop over all SL rungs (`_check_trailing_stop` currently modifies the single `_sl_order_id`, `:1549-1593`), ledger schema for per-rung ids (`active_positions` has single `tp_order_id`/`sl_order_id` columns), heal-path and sim rung modeling, then removal of the Stage-1 startup gate. Explicitly NOT one big group with ocaType=2 (proportionate reduction across mixed-size rungs is ill-defined at IBKR and would silently change modeled exit economics — Impact-Reviewer risk A).

### Stage 4 (optional exit-path ordering hardening; lowest urgency once Stages 1-2 land)
Defer the time-barrier `close_position` submission until the cancelled legs have provably LEFT the open book (extend the existing `:1866-1885` discipline to the legs). MUST solve the kill-switch keying problem first (Impact-Reviewer risk D): the deferral guard `:6270-6274` keys on `_pending_exit_order_id`, which is unset during a legs-cancelled/no-exit-yet transition — set the pending sentinel BEFORE the cancels or add a bounded transition budget, else the kill switch can fire mid-transition and regress `291a9fd`. Same confirm-before-act discipline for the kill switch's own cancel-then-flatten (`:6298-6318`), bounded by the existing attempts pattern; a position with a still-resting stop is by definition not naked, so deferring one tick is fail-safe.

## 3. Why this does NOT re-introduce the historical failure modes
1. **Error 201 (the `4a50a4f` constraint):** `ocaGroup` is a shared string tag between the sibling children only; no field references the filled (terminal) parent order id. Children remain standalone `transmit=True` orders placed post-fill. A red-sentinel test pins `parentId` unset forever.
2. **Fill-priced brackets:** two-phase placement is untouched; children are still priced from the actual fill in `_place_bracket_children_on_fill`.
3. **Overnight stop reliability (`triggerMethod=1` rationale):** preserved byte-identical on the order; the residual unknown is IB's with-block holding behavior — explicitly a canary gate with a documented ocaType=3 fallback (2.7), not an assumption.
4. **Reconnect-false-flat fix (`246c598`) and the settle-confirm/kill-switch chain (`a1464d2`/`731ebed`/`291a9fd`):** untouched in Stage 1; Stage 2 keeps `_reset_position_state` immediate specifically to avoid re-keying that machinery; Stage 4 is quarantined behind its own redesign answer.
5. **Trailing-stop TRANSMIT-THEN-COMMIT:** modify flow unchanged (re-`placeOrder` same orderId, `adapters/ibkr_execution.py:239-282`). Known theoretical edge (Impact-Reviewer risk B): after a broker-side partial reduce, the cached `totalQuantity` is stale-larger and a modify could resurrect quantity — impossible at 1-lot sizing (cannot partial-fill), pinned by a Stage-1 test asserting modify preserves broker-reduced quantity in the canary, and structurally solved by Stage 3's qty-matched pairs.

## 5. Test cases that prove the fix (Stage-1/2 acceptance)
1. **Placement contract:** children carry one shared, per-placement-unique `ocaGroup`, `ocaType=2`, `parentId` unset (Error-201 red sentinel); tags differ across two placements, across two client ids with colliding order ids, AND across two heal re-placements (both called with `parent_order_id=0` — the collision the derivation ban exists to prevent).
2. **Fast fill-before-cancel-ack (race seam):** TP `Filled` then SL `Filled` delivered before any app cancel is processed -> Stage-2 reversal branch fires (CRITICAL + Telegram + health event + flatten submitted + `OCA_RACE_REVERSAL` ledger row), NOT UNRECOGNIZED-ignore; position ends flat. Assert the SHARED FLATTEN HELPER is invoked (mock exec client: `close_position` + cancel + `telemetry.close_position` called) — and assert `_check_naked_position()` itself is NOT relied upon (it must remain a caller of the helper, with its `_active_trade_id` guard intact). Assert `get_cached_position` is used and the mock's `get_position` is NEVER called from this branch (in-callback blocking-reconnect regression guard, A-2).
3. **Disconnect replay:** leg fills while disconnected (no live callback; only `get_executions` records) -> single fill: reconciler books close and the sibling is (a) already broker-cancelled in the OCA world and (b) registry-matched if its late event replays. Both-legs-filled variant -> detected as reversal, not "healthy non-flat".
4. **Partial fill:** TP fills 2/3 (`status != Filled`) -> no reset, no software cancel; broker-side SL sits at reduced qty (sim seam asserts reduce-by-filled); remainder SL fill books correct final quantities.
5. **Trailing modify in flight:** (a) modify transmitted, then SL fills at OLD price replayed -> single booking, loud handling; (b) modify AFTER a partial reduce -> SL quantity must remain reduced (risk-B pin; canary scenario); (c) after `_check_trailing_stop` mutates `auxPrice` and `modify_order` re-transmits the SAME Order object, assert `ocaGroup`/`ocaType` on that object are UNCHANGED — a moving stop must not fall out of its OCA pairing.
6. **Heal path:** missing SL with surviving TP -> heal cancels the survivor and re-places BOTH legs under ONE fresh group (no mixed-group bracket ever rests).
7. **Sign check (D2):** pending exit retired, settled returns opposite sign -> NO re-arm; CRITICAL + flatten path; ledger truthful.
8. **Startup gate:** `exit_mode=TIERED` + `max_position_size>1` -> refuse to start, named error; 1-lot config starts normally and places exactly one TP rung.
9. **Kill-switch non-regression:** deferral keying scenarios from `291a9fd` stay green byte-identical in Stages 1-2.
10. **Paper canary checklist (operator):** entry->TP fill, entry->SL fill, overnight session with resting OCA bracket (verify stop state — the ocaType=2-vs-3 decision gate), mid-hour disconnect with leg fill while down, trailing modify on a live OCA SL, `broker_audit.py` group report.

## 6. Alternatives considered and rejected
- **Restore `parentId` brackets:** re-introduces Error 201 (the exact historical failure). Rejected.
- **Full bracket at entry time (`place_bracket_order` path):** prices children from the submission price, not the fill — re-introduces the mispricing the two-phase design exists to fix. Rejected.
- **App-side-only hardening (faster cancels, tighter loops):** cannot close R2 (disconnect) even in principle; the window exists by construction when OCO lives in the app. Rejected as primary (kept as Stage-2 belt-and-braces).
- **Do nothing:** the sim/backtest already assume atomic OCA (`simulated_execution.py:635-650` — same-bar conflict resolved pessimistically, sibling removed atomically), so live carries a failure mode the model stack cannot see, with ~18% of historical exits already filling outside the handler's observation window. Rejected.
